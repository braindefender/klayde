# klayde — обзор проекта

## 1. Что это

`klayde` — генератор раскладок клавиатуры из декларативных схем.
Вход: один или несколько TOML-файлов из `layouts/`.
Выход: файлы раскладок под конкретные ОС.

Текущий скоуп: **только Windows (`.klc`)**.
Linux и macOS — out of scope для генерации, но CLI уже сейчас принимает их
в параметре `--os` и архитектура закладывает общий интерфейс генераторов.

Приложение **не** создаёт `.exe`/`.dll`/`.msi`.
Это делает сам MSKLC вручную из наших `.klc`. Наш продукт — корректный `.klc`,
который MSKLC открывает без ошибок и предупреждений.

## 2. Сквозной процесс (конвейер)

Программа работает строго в три фазы, каждая следующая запускается только
если предыдущая прошла без ошибок:

**Фаза A. Разбор аргументов и поиск входов.**
CLI разбирает `--os` и путь до схемы. Если путь не задан — берутся все
`*.toml` из `layouts/`. Если `--os` не задан — генерируем для всех известных
ОС (`windows,macos,linux`), из которых реально работают только реализованные
генераторы. Нереализованные честно сообщают `not implemented` и не падают.

**Фаза B. Загрузка и валидация.**
Для каждого TOML-файла: проверка сырого текста (правило `'''`), парсинг TOML,
проверка структуры секций, геометрии сеток, содержимого ячеек, ссылок на
лигатуры, когерентности `caps`/`caps_shift`, маппируемости в Unicode.
Ошибки собираются по всем файлам и печатаются с точными координатами
(файл, секция, строка/столбец сетки). При хотя бы одной ошибке генерация
не начинается, процесс завершается с ненулевым кодом.

**Фаза C. Генерация.**
Каждая валидная схема преобразуется в каноническую внутреннюю модель
`LayoutSpec`, затем выбранные генераторы ОС превращают её в текст раскладки.
Windows-генератор дополнительно использует два статических артефакта:
таблицу позиций `(строка, колонка) -> (scancode, VK, Ctrl-колонка, Cap-зона)`
и таблицу соответствия `символ -> unicode-код + английское имя`.
Результат пишется в UTF-16LE с BOM и CRLF в выходной каталог
(предложение: `build/windows/<Имя раскладки>.klc`).

## 3. Ключевые проектные решения

1. **TOML — единственный формат входа.** Никаких JSON/YAML. Поля сеток —
   строго literal-строки `'''...'''`, чтобы обратный слэш `\` не escap'ился
   парсером. Проверка этого правила делается по сырому тексту до парсинга.
2. **Сетка фиксирована: 5 строк по 10 колонок.** Все шесть примеров в
   `layouts/` имеют именно такую геометрию. Позиционная таблица Windows
   (см. `docs/05-position-map.md`) жёстко привязана к ней. Сетки с другой
   геометрией — ошибка валидации, а не повод для эвристик.
3. **Cap определяется позицией, а не содержимым.** Строки 2–4 сетки
   (буквенная зона, 30 клавиш) всегда `SGCap`. Строки 1 и 5 (цифры и
   нижний ряд) всегда `Cap=0`. Это выведено из эталонов: даже символ `~`
   в буквенной зоне имеет `SGCap`, а запятая/точка в нижнем ряду — `Cap=0`.
4. **Лигатуры — только через `@Имя`.** Ячейка вида `@FatArr` обязана иметь
   определение в `[ligatures]`. Исключения, доступные без определения:
   `@None` (пусто, в KLC `-1`), `@Space` (`U+0020`), `@Nbsp` (`U+00A0`).
   В KLC ячейка лигатуры пишется как `%%`, а раскрытие уходит в секцию
   `LIGATURE` с указанием VK и номера шифт-состояния.
5. **Отсутствие `caps`/`caps_shift` = `caps=shift`.** Это дословно галочка
   `caps=shift` в MSKLC: для каждой `SGCap`-клавиши строка-расширение
   `-1 -1 0 ...` заполняется как `caps=shift`, `caps_shift=base`.
6. **Генераторы ОС — взаимозаменяемые стратегии** за общим интерфейсом
   `OsGenerator`. Сейчас реализуется только `WindowsKlcGenerator`,
   остальные — заглушки. Добавление Linux/macOS не меняет CLI, модель
   и валидацию.

## 5. Что намеренно не делаем

- Не собираем `.dll`/`.exe`/`.msi`, не запускаем `msklc.exe`.
- Не поддерживаем dead keys (в примерах их нет; символ `@` в конце ячейки
- Не угадываем геометрию и не чиним ошибки автоматически. Любая
  неоднозначность — это ошибка валидации с понятным сообщением.
