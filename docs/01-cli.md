# CLI-контракт

## 1. Точка входа

Пользователь запускает программу через Bun. Базовый вариант — скрипт `start`
с явными флагами:

```bash
bun run start -- --os="windows,macos,linux" --layout="layouts/universal-layout-ortho-merged.toml"
```

Для частых случаев в `package.json` заведены короткие скрипты-пресеты под каждую ОС:

```bash
bun run windows -- --layout="layouts/foo.toml"
bun run macos -- --layout="layouts/foo.toml"
bun run linux -- --layout="layouts/foo.toml"
bun run all
```

Фактическое содержимое скриптов:

- `windows` → `bun run index.ts -- --os=windows`;
- `macos` → `bun run index.ts -- --os=macos`;
- `linux` → `bun run index.ts -- --os=linux`;
- `all` → `bun run index.ts -- --os=windows,macos,linux` (явный эквивалент `start` без аргументов).

Двойной дефис `--` обязателен: всё, что после него, Bun передаёт программе,
а не себе. Текущий `index.ts` — заглушка (`Hello via Bun!`); при реализации
он станет тонким bootstrap, который вызывает `runCli(Bun.argv)`.

Будущее расположение точки входа — `src/main.ts`, а `index.ts` останется
совместимым шлюзом (реэкспорт вызова). Это предложение зафиксировано в
`docs/08-architecture.md`, на контракт CLI не влияет.

## 2. Аргументы

### `--os`

Список систем для генерации. Формат: запятая как разделитель, пробелы вокруг
допустимы, регистр не важен, дубликаты игнорируются.

```bash
--os="windows"
--os="windows,macos,linux"
--os windows
```

Правила:

1. Если флаг отсутствует — генерируем для всех известных ОС:
   `windows,macos,linux`.
2. Если значение пустое (`--os=""`) — это ошибка `E_OS_EMPTY`.
3. Каждый элемент списка нормализуется (`trim` + `lowercase`) и проверяется
   по белому списку `windows | macos | linux`. Неизвестное значение —
   ошибка `E_OS_UNKNOWN` с перечислением допустимых.
4. Порядок ОС в списке не влияет на результат; генераторы запускаются
   в фиксированном порядке `windows, macos, linux` ради детерминизма логов.
5. Генератор ОС, не реализованный на данный момент (macOS, Linux),
   для каждой схемы печатает предупреждение вида
   `skip: <файл> — генератор macos ещё не реализован`
   и завершается успешно. Это не ошибка: пользователь просил «все ОС»,
   Windows-артефакты при этом создаются.

### Путь до схемы

Имя флага — `--layout`.

```bash
--layout="layouts/universal-layout-ortho-merged.toml"
--layout layouts/foo.toml
```

Правила:

1. Если флаг отсутствует — входом считаются **все** `*.toml` в каталоге
   `layouts/` (только верхний уровень, без рекурсии, сортировка по имени).
2. Если каталог `layouts/` пуст или отсутствует — ошибка `E_NO_INPUTS`.
3. Если путь указывает на несуществующий файл — ошибка `E_LAYOUT_NOT_FOUND`.
4. Если путь указывает на каталог — берутся все `*.toml` внутри него
   (верхний уровень, сортировка по имени). Это обобщение правила 1.
5. Если передано несколько `--layout` — все собираются в один список,
   дубликаты убираются.
6. Расширение строго `.toml` (регистр не важен). Другие файлы игнорируются
   при сканировании каталога, но явное указание не-TOML файла — ошибка
   `E_LAYOUT_EXTENSION`.

### Дополнительные (опциональные) флаги

Предлагаются, но не обязательны для первой версии:

- `--out="build"` — корень выходного каталога (по умолчанию `build`).
  Подкаталог ОС добавляется автоматически (`build/windows`).
- `--verbose` — подробные логи по каждой стадии.

Любой неизвестный флаг — ошибка `E_ARGS_UNKNOWN` с подсказкой синтаксиса.

## 3. Алгоритм работы CLI

1. Отделить аргументы программы от аргументов Bun (всё после `--`).
2. Распарсить флаги в структуру `CliOptions { osList, layoutList, outDir, verbose }`.
   Ошибка парсинга — печать usage в stderr и выход с кодом 2.
3. Резолв входов в упорядоченный список файлов (см. раздел 2). Ошибки
   отсутствия входов — выход с кодом 2.
4. Для каждого файла выполнить фазу валидации (см. `docs/03-validation.md`).
   Собрать результаты. Напечатать все ошибки. Если есть хотя бы одна —
   выход с кодом 1, генерация не запускается ни для одного файла.
5. Для каждой валидной схемы и каждой запрошенной ОС вызвать соответствующий
   генератор. Записать файлы. Напечатать сводку `ok: <вход> -> <выход>`.
   Успех — выход с кодом 0. Ошибка записи — код 3.
6. Если все схемы были пропущены как `not implemented` (например, запрошен
   только macOS) — это всё равно успех с кодом 0, но сводка явно говорит,
   что артефактов создано ноль.

## 4. Коды выхода

- `0` — успех (включая случай «всё пропущено как not implemented»).
- `1` — есть ошибки валидации схемы; генерация не выполнялась.
- `2` — ошибка аргументов или входов (нечего валидировать).
- `3` — внутренняя ошибка генерации/записи (валидация прошла, но запись
  не удалась: нет прав, диск переполнен и т.п.).

## 5. Формат вывода

- Обычные сообщения и сводка — в stdout.
- Ошибки валидации и аргументов — в stderr.
- Каждая ошибка валидации — одна или несколько строк вида:

```text
error[E_GRID_GEOMETRY] layouts/foo.toml :: [layout].base: ожидалось 5 строк по 10 ячеек, получено 4 строки; строка 3 содержит 9 ячеек вместо 10
```

Код ошибки в квадратных скобках стабилен и документирован в `docs/03-validation.md`, чтобы на него можно было ссылаться.
Позиция внутри сетки всегда указывается как `строка, колонка` в терминах TOML-сетки (1-based), а не scancode.
