# Генерация раскладок для macOS (`.keylayout`): исследование и план

Статус: план, не реализация. Закрывает заглушку `MacosGenerator`
(`process/generators/macos/index.ts`, сейчас `skip: not implemented`).
Контракт CLI (`--os=macos`, docs/01) и интерфейс `OsGenerator` (docs/08)
не меняются.

## 1. Что генерируем

Один XML-файл на схему (без бандла и иконок в v1):

```text
<out>/macos/<main.name>.keylayout
```

Имя — `main.name` с пробелами (как `.klc` и как файлы upstream).
Установка — копированием вручную (генератор ничего не ставит в систему):

- `~/Library/Keyboard Layouts/<имя>.keylayout` (или `/Library/...` для всех
  пользователей), затем выбор в Settings → Keyboard → Input Sources
  (может потребоваться relogin);
- файл открывается в [Ukelele](https://software.sil.org/ukelele) —
  это второй ручной acceptance-канал помимо набора текста.

Наш продукт — валидный `.keylayout`, который macOS принимает
(появляется в Input Sources, все слои печатают).

## 2. Формат `.keylayout` (факты)

Источники: `Universal Layout Ortho/Standard.keylayout` из
`universal-layout` (Ukelele 359, разобраны построчно) + шпаргалка
по DTD (`lancejpollard`, сверена с файлами) + доки Ukelele.
Официальной спеки Apple в открытом доступе нет; ниже — факты,
подтверждённые чтением обоих файлов.

Структура (порядок строгий, проверен):

```xml
<?xml version="1.1" encoding="UTF-8"?>
<!DOCTYPE keyboard SYSTEM "file://localhost/System/Library/DTDs/KeyboardLayout.dtd">
<!-- сгенерировано klayde -->
<keyboard group="126" id="-123456" name="Universal Layout Ortho Merged" maxout="2">
    <layouts>...</layouts>
    <modifierMap id="mods" defaultIndex="0">...</modifierMap>
    <keyMapSet id="ulom">...</keyMapSet>
    <keyMapSet id="zzstub">...</keyMapSet>
</keyboard>
```

Факты, на которые опирается генератор:

1. `group="126"` — хардкод для кастомных раскладок (подтверждено обоими
   файлами и шпаргалкой). `name` — `main.name`.
2. `id` — у Ukelele случайный отрицательный int32 (у upstream `-24174`
   и `-15810`), обязан различаться у разных раскладок. Наш генератор:
   детерминированный FNV-1a от `main.name`, отображённый на отрицательный
   int32 (стабилен между прогонами; задокументировать формулу в коде).
3. `maxout` — максимум UTF-16 единиц, выдаваемых одним нажатием.
   Правило: `max(1, максимальная длина used-лигатур в UTF-16 единицах)`.
   В upstream `maxout="2"` при 2-символьных лигатурах — сходится.
   (Вне BMP в наших схемах нет; astral дал бы 2 единицы на символ —
   формула это учитывает.)
4. Элемент `keyboard` содержит ровно один `<layouts>`, один или более
   `<modifierMap>`, один или более `<keyMapSet>`; `<actions>`
   и `<terminators>` — **опциональны** (шпаргалка по DTD). Наших dead keys
   нет (в TOML ни одного), поэтому оба элемента **не пишем вообще**:
   файл короче upstream в разы (64 КБ → ~15 КБ) без потери смысла.
5. `mapIndex` в `keyMapSelect` — contiguous от 0 (реализация macOS —
   массив). Наш набор — 8 карт, как upstream `f4` (раздел 4).
6. Ключ без вывода — `output=""` (прецедент upstream: `code 65` пуст
   во всех картах). Пропуск элемента `<key>` означает fallback системного
   поведения — для наших 50 позиций не используется никогда.
7. Проверка без Mac: доступные нам проверки — XML-wellformedness
   (`DOMParser` в тестах), детерминированные golden-снапшоты,
   `plutil -lint` — только на Mac (ручной шаг). Полноценного
   `xkbcomp`-аналога под Linux/Windows нет — зафиксировано в рисках.

## 3. Привязка сетки 5×10 к macOS keycode

macOS-коды — физические (ADB), отличаются и от Windows-SC, и от XKB.
Привязка фиксированной таблицей `mac-5x10-v1`, порядок строк в файле —
r1→r5, c1→c10 (как в upstream), тест «50 записей» по образцу фазы 3:

| Ячейка     | macOS-код                   | Позиция US-прототипа           |
| ---------- | --------------------------- | ------------------------------ |
| r1c1–r1c10 | 18, 19, 20, 21, 23, 22, 26, 28, 25, 29 | Цифровой ряд (`1`→18 … `0`→29; внимание: `5`→23, `6`→22 — историческая ADB-причуда, сверено с upstream: код 22 несёт `6`, код 23 — `5`) |
| r2c1–r2c10 | 12–17, 16, 32, 34, 31, 35   | Верхний буквенный (`Q`→12 …)   |
| r3c1–r3c10 | 0–5, 4, 38, 40, 37, 41      | Домашний ряд (`A`→0 …)         |
| r4c1–r4c10 | 6–9, 11, 45, 46, 43, 47, 44 | Нижний буквенный (`Z`→6 …)     |
| r5c1       | 49                          | Пробел                         |
| r5c2       | 50                          | `` ` `` (наш OEM_3)            |
| r5c3       | 27                          | Минус (наш OEM_MINUS)          |
| r5c4       | 24                          | Плюс (наш OEM_PLUS)            |
| r5c5       | 33                          | `[` (наш OEM_4)                |
| r5c6       | 30                          | `]` (наш OEM_6)                |
| r5c7       | 42                          | `\` (наш OEM_5)                |
| r5c8       | 39                          | `'` (наш OEM_7)                |
| r5c9       | 10                          | ISO-клавиша (наш OEM_102)      |
| r5c10      | 65                          | Точка нумпада (наш DECIMAL)    |

Сверено с upstream: коды 12/0/6/49/50 несут контент тех же ячеек
(`q`/`a`/`z`/space/`'`); код 10 отсутствует в upstream везде
(их пробел — мы пишем явно, правило раздела 2.6).

## 4. Слои → keyMap (`modifierMap`, 8 карт)

Наш `modifierMap` — копия upstream `f4` дословно (побайтово идентичен
в обоих файлах, контентно-независим):

- map 0 (`none`) = `base`;
- map 1 (`anyShift`) = `base_shift`;
- map 2 (`caps`) = `caps`;
- map 3 (`anyShift caps`) = `caps_shift`;
- map 4 (`caps? anyOption`) = `altgr` (CapsLock на AltGr не влияет —
  как в KLC, где caps-расширения покрывают только base/shift);
- map 5 (`anyShift caps? anyOption`) = `altgr_shift`;
- map 6 (`... anyControl`) = control-passthrough, статика;
- map 7 (`... command`) = command-psthrough, статика.

Следствия (все — хорошие новости, в отличие от XKB):

- **caps — нативно**: карты 2/3, отдельных расширений не нужно.
  Слои `caps`/`caps_shift` обязательны и пишутся как есть
  (включая `@Trans`-копии base/base_shift — резолв делает валидатор;
  Cap 0/1-оптимизация существует только в KLC-генераторе).
  Параметр `[main].caps_is_shift` отображение не меняет: при `true`
  содержимое и так связано с base (swap/`@Trans`), при `false` —
  независимо; в обоих случаях карты 2/3 — прямые копии слоёв.
  Никаких `W_`/`G_`-кодов про caps на macOS нет.
- **Лигатуры — нативно** (раздел 5).
- `@None` → `output=""` (прецедент upstream: код 65). Все 50 кодов
  пишутся в картах 0–5 всегда — того же класса решение, что `[ NoSymbol ]`
  в XKB и по той же причине (никаких fallback-дырок).
- Карты 6/7 — статические константы, извлечённые из upstream
  (побайтово идентичны в обоих файлах; от контента не зависят:
  control/command-выходы позиционные — `Ctrl+Q → 0x11`, command даёт
  строчную букву). Для кода 10, отсутствующего в upstream, в картах 6/7
  пишем `output=""` (осознанное решение без прецедента, зафиксировано
  тестом).
- `layouts`-блок (8 диапазонов keyboard-type → mapSet/modifiers)
  и stub-`keyMapSet` (один `code 512`) — дословные константы из upstream
  (идентичны в обоих файлах). Наш `keyMapSet id` = `short_name`
  в нижнем регистре (`ulom`); `modifierMap id` = `mods`
  (осмысленные имена вместо `16c`/`f4`).
- F-клавиши и прочие коды вне наших 50 (в upstream 16c их 103):
  статический passthrough-блок, извлечённый из upstream
  (96 строк карт 0/1 идентичны между файлами) — нулевой риск fallback,
  детерминизм сохранён.

## 5. Лигатуры: на macOS проблемы нет

В отличие от XKB, `.keylayout` умеет многосимвольный вывод из коробки:
`output` принимает произвольную строку (Ukelele-фича «multiple-character
strings», upstream это использует):

```xml
<key code="40" output="=&#x003E;"/>
```

Правила:

- `@Имя` → `output="<раскрытие как есть>"` (2–4 символа из V4);
  XML-экранирование — по разделу 7;
- `maxout` покрывает самую длинную used-лигатуру (раздел 2.3);
- `%%`-эквивалентов, секций раскрытия и `G_`/`W_`-кодов про лигатуры
  на macOS нет — в этом главный выигрыш формата;

## 6. CapsLock: нативно, без кодов

Карты 2/3 (`caps` / `anyShift caps`) — штатный CapsLock macOS.
Слои `caps`/`caps_shift` пишутся как есть, все 50 кодов в обеих картах.
Параметризованные тесты: все карты 2/3 сверяются со значениями слоёв
из TOML (зеркало тестов caps фазы 5).

## 7. Кодирование `output`

- XML-escape: `&`→`&amp;`, `<`→`&lt;`, `>`→`&gt;`, `"`→`&quot;`
  (обязательно: `"` встречается в сетках!), `'` — как есть
  (атрибуты в двойных кавычках), управляющие символы — `&#xHHHH;`;
- весь остальной Unicode — сырым UTF-8 (как upstream: сырая кириллица
  рядом с `&#x0027;` — практика смешанная, наше правило детерминировано);
- `@Space` → ` ` (U+0020), `@Nbsp` → ` ` (U+00A0, сырым),
  `@None` → `output=""`;
- кодирование — чистые функции (`encodeOutput`), подменяемые в тестах;
  таблица не нужна (в отличие от `unicode.json`/`xkb-keysyms.json):
  имена символов в `.keylayout` отсутствуют вообще.

## 8. Интерфейс и коды

```ts
class MacosGenerator implements OsGenerator {
  readonly os = "macos" as const;
  generate(spec: ValidatedSpec, outDir: string): Promise<GenerateResult>;
}
```

- Выход: `<out>/macos/<main.name>.keylayout`, UTF-8 без BOM, CRLF
  (как upstream),
  запись атомарная (временный файл + rename, как `klcWriter.ts`).
- `G_`/`W_`-кодов v1 не предвидится: лигатуры и caps представляются
  нативно, astral-символы — сырым UTF-8 (maxout считает UTF-16 единицы).
- Defense in depth перед записью: карты 0–5 содержат все 50 кодов;
  карты 2/3 равны слоям `caps`/`caps_shift`; `maxout` равен максимуму
  UTF-16-длин; XML well-formed (проверка в тестах); ни одного имени
  лигатуры в тексте.

## 9. Установка и тестирование

Автоматизировано (тесты генератора, без Mac):

- XML-инварианты сгенерированных файлов (без `DOMParser` — его нет
  в Bun): баланс тегов, отсутствие голых `&`/`<`/`"` внутри значений
  `output` (проверка по `&amp;|&lt;|&gt;|&quot;|&#x…;`), round-trip
  `encodeOutput`→unescape для tricky-ячеек (`"`, `&`, `<`, NBSP)
  + точечные assertions значений (`output="=>"` на коде 40
  в картах 4/5 и т.п.);
- golden-снапшоты: наши образцы в `tests/golden/*.keylayout`
  (пишутся нами, ревьюятся построчно; файлы upstream — только референс,
  не golden, см. раздел 11);
- юнит-тесты таблицы привязки (50 записей) и `encodeOutput`
  (экранирование, NBSP, пустые, maxout);
- `plutil -lint` — только на Mac (ручной шаг).

Ручной acceptance на Mac (два канала):

1. Скопировать `.keylayout` в `~/Library/Keyboard Layouts/`, выбрать
   в Input Sources (relogin при необходимости), набрать все 4 слоя +
   Caps / Caps+Shift по каждой клавише, сверить с TOML;
2. Открыть файл в Ukelele — структура должна читаться без ошибок.

## 10. План внедрения (по шагам)

1. **Таблица привязки** `process/generators/macos/positions.ts`
   (`mac-5x10-v1`, 50 записей: `(r,c) → keycode`) + тест «50 записей».
2. **`keylayoutLayout.ts`** (`encodeOutput`, `escapeXmlAttr`): карты 0–5
   из слоёв (`@None`→`""`, лигатуры строками), `trans` → `G_INTERNAL`,
   карты 6/7 + F-key passthrough + `layouts`/stub/`modifierMap`
   как константы (`keylayoutHeader.ts`), `key <CAPS>` не трогаем
   (код 57 отсутствует в картах — CapsLock работает через `caps`-селектор).
3. **`keylayoutWriter.ts`**: шапка/DOCTYPE/комментарий, `keyboard`-тег
   (`group 126`, детерминированный `id`, `maxout`), сборка, CRLF
   (как upstream), UTF-8 без BOM, атомарная запись в `<out>/macos/`
   с сохранением структуры `layouts/` (общий `resolveOsOutDir`).
4. **`index.ts`**: `MacosGenerator`, подключение к реестру
   (реестр уже есть — только замена заглушки).
5. **Golden-снапшоты + XML-тесты**, регресс `bun run all`.
6. Ручной acceptance на Mac (два канала из раздела 9).

## 11. Сверка с существующей реализацией

Файлы `Universal Layout Ortho/Standard.keylayout` (Ukelele 359):
`modifierMap`, `layouts`-блок, stub-сетка, карты 6/7, F-key passthrough —
побайтово идентичны (заимствуем как константы); `actions`/`terminators`
(64 КБ dead-key boilerplate) — не заимствуем (наших dead keys нет,
элементы опциональны по DTD).

Дрейф контента vs наши TOML (поэтому не golden, только референс):

- цифровой ряд — символы первыми (`!` в map0): соответствует
  `*-inverted.toml`, не прямым схемам;
- caps r4c8 (код 33) = `,` — не сходится ни с TOML (`&`), ни с KLC-эталоном
  (`бе`): третья ревизия данных;
- код 65 (`KPDL`) пуст во всех картах, хотя TOML содержит `./,`;
  наш генератор следует TOML (эмитит контент);
- код 10 отсутствует везде; наш генератор пишет явно (раздел 2.6).

Вердикт — как с XKB: референс, не golden. Подтверждённые находки
внесены в разделы 2–4 выше.

## 12. Риски

- Нет автоматической проверки «macOS принимает файл» вне Mac
  (аналога `xkbcomp` под Linux/Windows нет) — mitigated: строгие
  golden-снапшоты + `DOMParser` + два ручных канала (набор, Ukelele).
- Невидимое поведение незамаппленных кодов (F-клавиши покрыты статикой,
  но новые клавиатуры Apple могут добавить коды) — mitigated: passthrough
  скопирован из актуального upstream; fallback = системный дефолт.
- `id`-коллизии при установке рядом с upstream-файлами — mitigated:
  детерминированный хэш от имени вместо случайного; разные имена —
  разные id по построению.
- Поведение CapsLock с зажатым Option (`caps?` в картах 4/5) повторяет
  upstream дословно — mitigated: соответствует KLC-семантике
  (Caps не трогает AltGr), сверяется ручным acceptance.
