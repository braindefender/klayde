# Генерация `.klc` для Windows: алгоритм

Вход: `ValidatedSpec` (см. `docs/03-validation.md`: матрицы 5×10 всех 6
слоёв, карта лигатур, метаданные). Выход: текст `.klc` в UTF-16LE
с BOM и CRLF. Побочных эффектов, кроме записи одного файла, нет.

## 1. Подготовка данных

1. Загрузить таблицу позиций `ortho-5x10-v1` (`docs/05-position-map.md`):
   50 записей `(r, c, sc, vk, capZone, ctrl)`.
2. Загрузить таблицу Unicode `char -> (hex, UPPER_NAME)`
   (`docs/07-unicode-ligatures.md`).
3. Резолв каждой ячейки сетки в промежуточное значение `CellValue`:
   - `None` → маркер пустого;
   - `Space` → `U+0020`;
   - `Nbsp` → `U+00A0`;
   - `LigatureRef(имя)` → маркер лигатуры с раскрытием из карты
     (массив кодпоинтов уже проверен валидатором);
   - `Char(c)` → один кодпоинт.
4. Определить для каждой из 50 клавиш пятёрку состояний
   `(s0, s1, s2ctrl, s6, s7)`, где `s0 = base[r][c]`, `s1 = base_shift[r][c]`,
   `s6 = altgr[r][c]`, `s7 = altgr_shift[r][c]`, а `s2ctrl` — константа `ctrl`
   из таблицы позиций (не из TOML). `@Trans` к этому моменту уже раскрыт
   валидатором: в `caps` лежит копия `base`, в `caps_shift` — копия
   `base_shift` (включая лигатуры).
5. Определить пару `caps` для `SGCap`-позиций только из явных слоёв:
   `caps = caps_layer[r][c]`, `capsShift = caps_shift_layer[r][c]`
   (оба слоя обязательны). Для `Cap0`-позиций пара не нужна. Действует
   Cap-оптимизация (раздел 3, пп. 2–4): прозрачность → `Cap 0`,
   swap → `Cap 1`, иначе `SGCap`. Не-буквы в `SGCap`-зоне (ряды 2–4)
   размечаются `@Trans` и дают `Cap 0` — системный CapsLock их не трогает.

## 2. Кодирование одного значения в колонку `LAYOUT`

Функция `encodeCell(value)` возвращает строку колонки:

- `None` → `-1`;
- `Space` → `0020`;
- `Nbsp` → `00a0`;
- `Char(c)` → 4-hex в нижнем регистре с дополнением нулями до 4 знаков
  (`U+002D → 002d`, `U+00AB → 00ab`, `U+2014 → 2014`). Символы вне BMP
  (код > `FFFF`) — отдельная история: KLC исторически UCS-2; генератор
  первой версии отвергает их ошибкой генерации `G_UNICODE_ASTRAL`
  (валидатор их пропускает, генератор — нет), чтобы не писать неверные
  суррогаты молча. Это осознанное ограничение, зафиксированное в тестах.
- `LigatureRef` → `%%` (раскрытие уходит в `LIGATURE`, см. раздел 4).

Комментарий `// ...` для строки собирается из имён символов тех же значений
(для лигатур — имена раскрытия через ` + `, для `-1` — `<none>`, для `%%` —
имена раскрытия лигатуры; формат повторяет эталон).

## 3. Построение секции `LAYOUT`

Для каждой записи таблицы позиций в каноническом порядке эталона
(см. `docs/05-position-map.md`, раздел 3):

1. Вычислить `c0 = encodeCell(s0)`, `c1 = encodeCell(s1)`,
   `c2 = ctrl` (готовая строка `001b` или `-1`),
   `c6 = encodeCell(s6)`, `c7 = encodeCell(s7)`.
   Исключение: `SC 39` (`SPACE`) — `c7` всегда `-1` (см. раздел 4
   позиционной таблицы).
2. Определить `cap`: `0` для `Cap0`-зоны; для `SGCap`-зоны —
   `0`, если `caps==base` и `caps_shift==base_shift` (прозрачность,
   CapsLock без эффекта — сюда попадают не-буквы с `@Trans/@Trans`);
   `1`, если `base!=shift`, `caps==shift` и `caps_shift==base`
   (нативный caps=shift MSKLC); иначе `SGCap`.
3. Записать строку `SC\tVK\t\tCap\tc0\tc1\tc2\tc6\tc7\t\t// <комментарий>`.
   Форматирование — табуляции как в эталоне (после `VK` две табуляции,
   после последней колонки две табуляции перед `//`). Точное число
   табуляций фиксируется golden-тестом, а не «на глаз».
4. Если `Cap = SGCap`: следующей строкой записать расширение
   `-1\t-1\t0\tcaps\tcapsShift\t\t// <комментарий caps>`,
   где `caps`/`capsShift` кодируются той же `encodeCell`. Лигатура
   допустима в caps только при `Cap 0`/`Cap 1` (переиспользует `Mod#`
   0/1 из base, отдельных записей `LIGATURE` не требует — как `J`
   в `caps_shift_test.klc`); при `SGCap` MSKLC не предоставляет `Mod#`
   для caps-расширений, поэтому лигатура — ошибка генерации
   `G_CAPS_LIGATURE` с понятным текстом.

## 4. Построение секции `LIGATURE`

1. Пройти все 50 клавиш в порядке `LAYOUT` и для каждой проверить четыре
   состояния с потенциальными лигатурами: `s0 (Mod# 0)`, `s1 (Mod# 1)`,
   `s6 (Mod# 3)`, `s7 (Mod# 4)`. Состояние `s2ctrl` лигатур не имеет.
   На практике в примерах лигатуры только в `s6/s7` клавиши `K`
   (`r3c8`, `VK K`), но алгоритм общий: любая `%%` в `LAYOUT` обязана иметь
   парную строку здесь.
2. Для каждой найденной лигатуры записать строку
   `VK\t\tMod#\tкод0\tкод1\t[код2]\t[код3]\t\t// <ИМЯ0 + ИМЯ1 ...>`.
   Коды — hex раскрытия значения лигатуры. `VK` — имя из таблицы позиций.
3. Сортировка строк: порядок обхода (scancode, затем `Mod#` по возрастанию).
   Совпадает с эталоном (`K 3`, затем `K 4`).
4. Если лигатур нет — секция всё равно пишется с заголовком и комментариями,
   но без строк данных (как пустой `LIGATURE` в системных KLC без лигатур).
   Заголовок-комментарий копируется дословно:
   `//VK_\tMod#\tChar0\tChar1\tChar2\tChar3` и подчёркивание.

## 5. Сборка файла целиком

Порядок секций и дословные шаблоны — из `docs/04-klc-format.md`:

1. Шапка `KBD/COPYRIGHT/COMPANY/LOCALENAME/LOCALEID/VERSION` из метаданных
   (локаль — дефолты до решения из `docs/02-toml-schema.md`).
2. `SHIFTSTATE` — дословная константа из пяти строк.
3. `LAYOUT` — заголовок + 50 основных строк + 30 расширений `SGCap`
   (итого 80 строк данных; в эталоне блок занимает 85 строк с заголовками
   и пустыми — golden-тест сверяет точно).
4. `LIGATURE` — по разделу 4.
5. `KEYNAME`, `KEYNAME_EXT` — дословные константы из эталона.
6. `DESCRIPTIONS` — `0409\t<main.name>`. Префикс `0409` — суффикс `LOCALEID`;
   берётся из выбранной локали программно, а не хардкодом.
7. `LANGUAGENAMES` — до решения: то же значение, что `DESCRIPTIONS`.
   Отличие от эталона (`...Ortho` без последнего слова) фиксируется как
   известное и покрывается тестом с пометкой.
8. `ENDKBD` и завершающий перевод строки.

Кодирование: собрать весь текст с `\n`, затем заменить на `\r\n`,
закодировать в UTF-16LE с BOM (`FF FE`) и записать. Имя файла:
`<main.name>.klc` (как в эталонах: `Universal Layout Ortho Merged.klc`),
каталог: `<out>/windows/`. Перезапись существующего файла — молча
(входной набор уже проверен на дубли в V9).

## 6. Проверки генератора (defense in depth)

Хотя валидатор гарантирует инварианты, генератор перед записью выполняет
дешёвые ассёрты с кодами `G_...`: число строк `LAYOUT` равно 50+30,
каждая `%%` имеет парную запись `LIGATURE`, каждая запись `LIGATURE`
имеет парную `%%`, нет `G_CAPS_LIGATURE`, нет `G_UNICODE_ASTRAL`.
Нарушение — исключение с понятным текстом, а не битый файл. Файл пишется
атомарно (во временный рядом + rename), чтобы прерванный прогон не оставлял
половинчатый `.klc`.

## 7. Сложность и производительность

Алгоритм линеен от числа клавиш (50) и лигатур (единицы). Никакой асинхронности
внутри генерации одного файла не нужно. Параллелизм между файлами допустим,
но не обязателен: даже сотни схем обрабатываются за миллисекунды без учёта I/O.
Детерминизм важнее скорости: сортировки и порядки фиксированы, хеш-мапы
с недетерминированным порядком для вывода не используются.
