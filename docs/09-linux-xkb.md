# Генерация раскладок для Linux (XKB): исследование и план

Статус: реализовано (`LinuxXkbGenerator`: `positions.ts`, `keysyms.ts` +
`data/xkb-keysyms.json`, `xkbLayout.ts`, `xkbWriter.ts`; golden-снапшоты
в `tests/golden/linux/`).
Контракт CLI (`--os=linux`, docs/01) и интерфейс `OsGenerator` (docs/08)
не меняются.

## 1. Что генерируем

Один текстовый файл `xkb_symbols` на схему (без расширения —
так требуют XKB-утилиты: `setxkbmap -layout <имя>` ищет файл с этим именем):

```text
<out>/<rel>/linux/<main.short_name>
```

Имя — `short_name` (одно слово, уникален среди схем); подкаталог `<rel>`
повторяет структуру `layouts/` (общий `resolveOsOutDir`, как у Windows:
`layouts/universal-layout/ortho/x.toml` → `build/universal-layout/ortho/linux/ULOM`).

Установка — копированием вручную (генератор ничего не ставит в систему):

- Wayland (libxkbcommon): `~/.config/xkb/symbols/<имя>`, выбор раскладки
  средствами окружения;
- X11: `/usr/share/X11/xkb/symbols/<имя>` (+ опционально регистрация
  в `rules/evdev.xml` для GUI-переключателей) либо
  `setxkbmap -I~/.config/xkb -layout <имя>`.

Наш продукт — корректный symbols-файл, который `xkbcomp` собирает
без ошибок и предупреждений. Ручной acceptance — набор текста
и сверка слоёв (см. раздел 8).

## 2. Формат `xkb_symbols` (факты)

Минимальный файл (проверено по документации libxkbcommon и `xkeyboard-config`):

```text
default partial alphanumeric_keys
xkb_symbols "ULOM" {
    include "pc+inet(evdev)";
    include "level3(ralt_switch)";
    name[Group1]= "Universal Layout Ortho Merged";
    name[Group2]= "Universal Layout Ortho Merged (caps)";
    key <CAPS> { [ ISO_Next_Group ] };
    key <AE01> { type[Group1]="FOUR_LEVEL", type[Group2]="FOUR_LEVEL", symbols[Group1] = [ 1, exclam ], symbols[Group2] = [ 1, exclam ] };
    key <AD01> { type[Group1]="FOUR_LEVEL_ALPHABETIC", type[Group2]="FOUR_LEVEL_ALPHABETIC", symbols[Group1] = [ q, Q, Greek_psi, Greek_PSI ], symbols[Group2] = [ Cyrillic_be, Cyrillic_BE, Greek_psi, Greek_PSI ] };
    key <SPCE> { type[Group1]="FOUR_LEVEL", type[Group2]="FOUR_LEVEL", symbols[Group1] = [ space, space, nobreakspace, nobreakspace ], symbols[Group2] = [ space, space, nobreakspace, nobreakspace ] };
};
```

Пример выше — режим `caps_is_shift=false` (merged, две группы).
При `caps_is_shift=true` (english/russian, стандарт) групп одна:
строки `name[Group2]`, `key <CAPS>` и все `type[Group2]`/`symbols[Group2]`
отсутствуют (ср. системные дампы `docs/xkb-en_US.xkb`,
`docs/xkb-ru_RU.xkb`). Подробности — раздел 4.

Факты, на которые опирается генератор:

1. Строка клавиши: `key <КОД> { [ l1, l2, l3, l4 ] };` — от 1 до 4 keysym
   на группу. Хвост `-1` из нашей модели не пишется; `@None` в середине —
   `NoSymbol` на своём месте (уровни нельзя сдвигать, раздел 4).
2. Уровни 3–4 выбираются модификатором `ISO_Level3_Shift` (обычно правый Alt).
   Строка `include "level3(ralt_switch)"` внутри секции делает раскладку
   самодостаточной: пользователю не нужен `-option lv3:...`.
3. Тип клавиши — всегда явный, отдельно на группу:
   `type[GroupN]="FOUR_LEVEL_ALPHABETIC"` для рядов 2–4,
   `type[GroupN]="FOUR_LEVEL"` для рядов 1/5 (включая SPCE —
   осознанно строже upstream, где у SPCE типа нет; поведение
   либо идентично, либо чинит потенциально мёртвые уровни 3–4).
   Дефолтных типов не используем: явность дешевле расследования.
   Проверяется прогоном `xkbcomp -w 10` на реализации.
4. Keysym — каноническое имя из `keysymdef.h` / таблицы
   `xkbcommon-keysyms.h` (префикс `XKB_KEY_` опускается): `q`, `comma`,
   `guillemetleft`, `emdash`, `EuroSign`, `nobreakspace`,
   `Cyrillic_be` / `Cyrillic_BE`, `Cyrillic_io` / `Cyrillic_IO`,
   `Greek_psi` / `Greek_PSI` — либо форма `U00AB` для символов без имени.
   Правила выбора имени: первое перечисленное в `keysymdef.h` —
   каноническое (алиасы вроде `guillemotleft`, `Greek_lambda`
   deprecated и не используются); регистр значим (строчные буквы —
   строчное имя, заглавные — заглавное: `Greek_lamda`, а не `lambda`).
   Точное отображение hex→имя фиксирует `data/xkb-keysyms.json`
   (раздел 6), а не алгоритм в коде.
5. Проверка синтаксиса без иксов: `xkbcomp -w 10 <файл> /dev/null`
   (предупреждения `-w 10` — тоже ошибки для нас) и
   `xkbcli compile-keymap --layout <имя>` из libxkbcommon.
6. Dead keys (`dead_acute` и т.п.) в наших схемах отсутствуют
   (в TOML нет ни одного; boilerplate про `@` в KLC относится только
   к Windows). Их поведение всё равно определяется не xkb-файлом,
   а Compose-таблицей на стороне клиента (libX11) — для нас неактуально.

## 3. Привязка сетки 5×10 к XKB-кодам

XKB-коды идут по физическим рядам staggered-клавиатуры, но каждая наша
ячейка `(r, c)` привязывается к одному коду фиксированной таблицей —
аналогично `positions.ts` (таблица версионируется отдельно,
`xkb-5x10-v1`, валидатор и генератор не меняются):

| Ячейка     | XKB-код   | Позиция US-прототипа           |
| ---------- | --------- | ------------------------------ |
| r1c1–r1c10 | AE01–AE10 | Цифровой ряд                   |
| r2c1–r2c10 | AD01–AD10 | Верхний буквенный              |
| r3c1–r3c10 | AC01–AC10 | Домашний ряд                   |
| r4c1–r4c10 | AB01–AB10 | Нижний буквенный               |
| r5c1       | SPCE      | Пробел                         |
| r5c2       | TLDE      | Клавиша `` ` `` (наш OEM_3)    |
| r5c3       | AE11      | Минус (наш OEM_MINUS)          |
| r5c4       | AE12      | Плюс (наш OEM_PLUS)            |
| r5c5       | AD11      | `[` (наш OEM_4)                |
| r5c6       | AD12      | `]` (наш OEM_6)                |
| r5c7       | BKSL      | `\` (наш OEM_5)                |
| r5c8       | AC11      | `'` (наш OEM_7)                |
| r5c9       | LSGT      | ISO-клавиша `<>` (наш OEM_102) |
| r5c10      | KPDL      | Точка нумпада (наш DECIMAL)    |

Соответствие проверено попозиционно: каждый Windows scancode из `docs/05`
сидит на той же физической клавише, что и XKB-код выше
(SC 02↔AE01 … SC 28↔AC11, SC 56↔LSGT, SC 53↔KPDL, SC 39↔SPCE).

Порядок строк в файле — порядок таблицы выше (r1→r5, c1→c10),
детерминирован и зафиксирован тестом. Все 50 позиций пишутся всегда:
полностью пустая клавиша (все слои `@None` после fallback'а лигатур,
т.е. наш r5c8) — это обычная клавиша со строкой `key <AC11> { [ NoSymbol ] };`.
Пропускать её нельзя: klayde — универсальное приложение, а не приложение
одного universal-layout, и пропущенная клавиша унаследовала бы определение
из `include "pc+us"` (там на AC11 — апостроф), что неверно для схем,
где ячейка осознанно пуста. (В KLC-генераторе действует обратное правило —
пропуск SC 28: там нет include-механизма, пропуск означает unmapped,
и эталоны это подтверждают. Правила различаются осознанно.)

## 4. Слои → уровни и группы

Отображение слоёв на уровни прямое: `base`→1, `base_shift`→2,
`altgr`→3, `altgr_shift`→4. `@None` в хвосте уровней опускается
(`[period, greater]` вместо `[period, greater, -1, -1]`);
`@None` в середине — `NoSymbol` на своём уровне
(`[a, A, NoSymbol, X]`): уровни привязаны к модификаторам, поэтому
сдвигать значения вверх нельзя. Валидатор V5/V6 допускает `@None`
на любом слое, так что середина — штатный случай, а не исключение;
что `xkbcomp` принимает `NoSymbol` в середине, подтверждает прогон
`xkbcomp -w 10` на реализации (раздел 8). Клавиша, пустая во всех
слоях, — `[ NoSymbol ]` (раздел 3, защита от наследования из `include`).

Группы выбирает `[main].caps_is_shift` (см. `docs/toml-schema.md`):

- `true` (стандарт, english/russian): **одна группа**
  Group1 = `base`→1, `base_shift`→2, `altgr`→3, `altgr_shift`→4.
  `name[Group2]` и `key <CAPS>` не пишутся, `ISO_Next_Group`
  в выводе отсутствует. CapsLock отрабатывает штатным типом
  `FOUR_LEVEL_ALPHABETIC` (ряды 2–4) — как в системных дампах
  `docs/xkb-en_US.xkb` и `docs/xkb-ru_RU.xkb`: там тоже одна группа
  без переключателя. Слои `caps`/`caps_shift` в вывод не попадают
  (их содержимое — swap/`@Trans`, т.е. та же информация, что в base).
- `false` (виртуальное переключение, merged): **две группы**
  (приём из `ulo_combo`, раздел 11 — CapsLock переключает группы
  через `key <CAPS> { [ ISO_Next_Group ] };`, поэтому обязательные
  слои `caps`/`caps_shift` маппятся во вторую группу, а не игнорируются):

- Group1: `base`→1, `base_shift`→2, `altgr`→3, `altgr_shift`→4;
- Group2: `caps`→1, `caps_shift`→2, `altgr`→3, `altgr_shift`→4 —
  уровни 3–4 дублируют Group1 (как в `ulo_combo`, где Group2 тоже
  четырёхуровневая): иначе после переключения группы по CapsLock
  XKB забыл бы, что AltGr-слои вообще существуют. На Windows паритет
  точный: CapsLock там не затрагивает AltGr-состояния (caps-расширения
  знают только 2 состояния), и дублирование воспроизводит именно это;
- Group2 = явные caps-уровни 1–2 (`caps`→1, `caps_shift`→2;
  `@Trans`-копии base/base_shift попадают сюда как есть —
  резолв делает валидатор), уровни 3–4 — дубли Group1;
- `key <CAPS> { [ ISO_Next_Group ] };` — только при `false`;
  стандартного CapsLock (Lock-модификатор) в наших раскладках нет
  осознанно: Lock никем не посылается (при `true` его роль играет
  `FOUR_LEVEL_ALPHABETIC`). Типы ключей Group2 — те же, что Group1
  (ряды 2–4 `FOUR_LEVEL_ALPHABETIC`, ряд 1/5 `FOUR_LEVEL`):
  обе группы четырёхуровневые, правило едино;
- `name[Group1] = "<main.name>"`, при `false` плюс
  `name[Group2] = "<main.name> (caps)"`.

Проверка соответствия: Group2 merged (`й`/`Й` на AD01…) совпадает
с Group2 `ulo_combo` — те же ячейки caps-слоёв по валидатору.
Типы Group1 — как раньше: ряды 2–4 `FOUR_LEVEL_ALPHABETIC`, ряд 1/5
`FOUR_LEVEL` (раздел 2).

## 5. Проблема лигатур (ключевой раздел)

Факт протокола: **одно нажатие клавиши в XKB даёт ровно один keysym**.
Механизма «нажал раз — получил строку `=>`» в `xkb_symbols` нет:

- `single key → single keysym` — базовый keymap;
- `single key → multiple keysyms` существует в API xkbcommon, но
  предназначен для combining-символов, клиенты X11 получают один keysym;
- обратная сторона — Compose: `multiple keys → string` (см. ниже),
  но это всегда **несколько нажатий**, а не одно.

Наши лигатуры (`@FatArr` → `=>`, `@ThinArr` → `->`) требуют именно
«одно нажатие — два символа», как в KLC-секции `LIGATURE`. Поэтому:

**Решение v1: предупреждение `W_LINUX_LIGATURE_FALLBACK` + fallback на `@None`.**
Каждая используемая лигатура, попадающая в вывод, даёт одно предупреждение
на ячейку (со координатами слоя/сетки, как в валидаторе) и кодируется как
пустая: уровень с лигатурой опускается, как `@None`. Если после fallback'а
клавиша становится полностью пустой — она пишется как `[ NoSymbol ]`
по правилу раздела 3 (пропуск запрещён: определение протекло бы из include). Печать предупреждений — в stderr в формате валидатора
(`warn[W_...] <файл> :: ...`), генерация при этом успешна: базовый набор
текста (все 4 слоя обычных символов) не страдает, а потеря лигатур —
громкая и проверяемая в тестах, а не молчаливая. Молчаливые варианты
без предупреждения (`=>` → `=`; `=>` → ничего) запрещены по-прежнему —
разница только в канале: предупреждение вместо блокирующей ошибки.

**Опция следующей фазой: XCompose-компаньон.** Формат Compose
(`man Compose(5)`) умеет отображать *последовательность* в строку:

```text
<Multi_key> <equal> <greater> : "=>"
```

Генератор может рядом с `.xkb` писать `<имя>.Compose`-фрагмент
(`include`-совместимый, для `~/.XCompose`) и печатать инструкцию
(назначить Compose-клавишу через `compose:menu` и др.). Это меняет
пользовательский жест (3 нажатия вместо 1), поэтому идёт отдельным
артефактом с явным согласием пользователя, а не тихой подменой.
Dead-key-обёртка (`dead_*` + допечатка) отвергнута: dead-клавиша
одиночным нажатием ничего не печатает — семантика «нажал–получил»
не воспроизводится в принципе.

Следствие для текущих схем: все используют `@FatArr`/`@ThinArr`
(валидатор подтверждает: `usedLigatures` непуст везде), значит
Linux-генерация v1 для них — всегда `W_LINUX_LIGATURE_FALLBACK`
(по одному на каждую ячейку-лигатуру) при успешном выходе. Это ожидаемо
и покрывается тестом: `--os=linux` на реальных схемах даёт код 0,
предупреждения в stderr и лигатурного мусора в выводе нет.

## 6. Имена keysym: `data/xkb-keysyms.json`

`data/unicode.json` (английские имена) для XKB не подходит: нужны имена
keysym (`comma`, а не `COMMA`). Стратегия кодирования символа:

1. ASCII-буквы/цифры — литерал имени (`a`, `Q`, `7`);
2. символы с каноническим именем в `keysymdef.h` — таблица:
   пунктуация (`comma`, `period`, `guillemetleft`, `emdash`, `ellipsis`,
   `rightarrow`, `multiply`, `EuroSign`, `nobreakspace`, ...) и все
   используемые буквы кириллицы/греческого (`Cyrillic_be` / `Cyrillic_BE`,
   `Cyrillic_io` / `Cyrillic_IO`, `Greek_psi` / `Greek_PSI`,
   `Greek_lamda` — каноническое, `Greek_lambda` deprecated);
3. всё остальное — форма `UXXXX` (`U2030`, `U2048`, `U20BD`);

Таблица-исключение живёт в `data/xkb-keysyms.json`
(`hex -> имя keysym`: пунктуация + вся используемая кириллица/греческий),
транскрибируется из `keysymdef.h` один раз (строго первоперечисленные,
канонические имена; сверено: `Cyrillic_be`/`Cyrillic_BE`,
`Cyrillic_io`/`Cyrillic_IO`, `Greek_psi`/`Greek_PSI`,
каноническое `Greek_lamda`), строится скриптом по инвентарю `layouts/`
(как в фазе 3) и покрывается тестом «каждый символ сеток имеет keysym»
плюс прогоном `xkbcomp -w 10`. Прямое кодирование в hex таблице
не требует — как и в `unicode.json`.

## 7. Интерфейс и коды

```ts
class LinuxXkbGenerator implements OsGenerator {
  readonly os = "linux" as const;
  generate(spec: ValidatedSpec, outDir: string): Promise<GenerateResult>;
}
```

- Выход: `<out>/linux/<main.short_name>` (без расширения, раздел 1),
  запись атомарная (временный файл + rename, как `klcWriter.ts`).
- `W_LINUX_LIGATURE_FALLBACK` — используемая лигатура в выводе, закодирована
  как пустая (раздел 5); предупреждение на ячейку, в stderr, генерация успешна.
  При `caps_is_shift=true` слои caps не кодируются вообще (в вывод
  не попадают), поэтому их лигатурные копии `@Trans` дублей не дают.
- Defense in depth перед записью: ровно 50 строк `key` (все позиции,
  пустые — `[ NoSymbol ]`, середина — `NoSymbol` на своём уровне, хвост
  обрезан); при `false` Group2 каждой клавиши = `[caps, caps_shift,
  altgr, altgr_shift]` после fallback'а; при `true` ни одна строка
  не содержит `Group2`/`ISO_Next_Group`; ни одного лигатурного артефакта;
  все keysym из таблицы/алгоритма (никаких `null`).

## 8. Установка и тестирование

Автоматизировано (тесты генератора):

- `xkbcomp -w 10 <файл> /dev/null` — ноль ошибок и предупреждений
  (пропуск, если `xkbcomp` отсутствует в CI, с явным `skip`);
- golden-тесты: сгенерированный `.xkb` для безлигатурных фикстур
  сверяется с зафиксированным образцом (образцы пишутся нами и ревьюятся
  построчно; существующие файлы upstream — только референс, не golden,
  см. раздел 11);
- Group1 всех схем — `[base, base_shift]` + дубли altgr/altgr_shift
  из Group1; при `false` Group2 — `[caps, caps_shift]` + те же дубли,
  `key <CAPS>` присутствует, групп ровно 2; при `true` группа ровно 1,
  `key <CAPS>` и `ISO_Next_Group` отсутствуют; AltGr работает
  в обеих (при `false` — в обеих группах);
- `W_LINUX_LIGATURE_FALLBACK` на всех 6 реальных схемах (по 2 на файл)
  при успешной генерации; отсутствие лигатурного мусора в выводе;
- юнит-тесты таблицы привязки (50 записей, как `positions.test.ts`)
  и кодирования keysym (включая `UXXXX`-край).

Ручной acceptance (единственный ручной шаг, как MSKLC в фазе 4):

1. Скопировать `.xkb` в `~/.config/xkb/symbols/` (Wayland) или
   `/usr/share/X11/xkb/symbols/` (X11).
2. Включить (`setxkbmap -layout <имя>` / окружение) и набрать все
   4 слоя каждой клавиши, сверить с TOML.
3. Проверить CapsLock, AltGr и Space-ряд отдельно.

    `NoSymbol`, полностью пустые — `[ NoSymbol ]`, типы обеих групп
    как Group1 (ряды 2–4 `FOUR_LEVEL_ALPHABETIC`, ряд 1/5 `FOUR_LEVEL`),
    fallback лигатур + `W_LINUX_LIGATURE_FALLBACK`, ассёрты;
4. **`xkbWriter.ts`**: сборка, LF-переводы строк (XKB-файлы — LF),
   UTF-8 без BOM, атомарная запись в `<out>/linux/`.
5. **`index.ts`**: `LinuxXkbGenerator`, подключение к реестру
   (реестр уже есть — только замена заглушки).
6. **Golden + `xkbcomp`-тесты**, регресс `bun run all`.
7. (Опционально, отдельно) **XCompose-компаньон** и README-инструкция.

## 10. Риски

- Wayland vs X11: разные пути установки и выбор раскладки —
  mitigated: README фиксирует оба пути, генератор от них не зависит.
- При `caps_is_shift=false` CapsLock переключает группы, а не лочит
  регистр: это осознанное отличие от стандартного CapsLock — mitigated:
  задокументировано здесь и в README-инструкции, сверяется ручным
  acceptance (набрать с Caps и Caps+Shift по каждой буквенной клавише);
  LED и Shift+Caps-жесты конкретных DE — пункт ручной проверки.
  При `true` CapsLock штатный (`FOUR_LEVEL_ALPHABETIC`, как в системных
  раскладках).
- Keysym-имена без канонического имени (редкая типографика) —
  mitigated: детерминированный fallback `UXXXX`, принимаемый `xkbcomp`.
- Лигатуры сводятся к пустым с громким предупреждением, пока нет
  компаньона — принято явно (раздел 5); риск «пользователь не заметит
  потерю `=>`» mitigated: предупреждение на каждую ячейку в stderr
  + тест на отсутствие лигатурного мусора в выводе.

## 11. Сверка с существующей реализацией

В `universal-layout/layouts/Linux/ortho/xkb/symbols/` лежат 3 файла:
`ulo_eng`, `ulo_rus` (одно групповые EN/RU) и `ulo_combo` (две группы:
EN + RU с кириллической базой в одном файле). Разбор по существу:

Что совпадает с планом (берём как референс):

- уровни 1–4 = наши 4 слоя, `include "level3(ralt_switch)"`, SPCE
  `[space, space, nobreakspace, nobreakspace]` — как наши сетки;
- ряды 2–4 — `FOUR_LEVEL_ALPHABETIC`, ряд 1/5 — `FOUR_LEVEL`;
- нелатиница — везде `UXXXX` (`U0439`, `U03C8`), именованных
  `Cyrillic_*`/`Greek_*` нет;
- приём `key <CAPS> { [ISO_Next_Group] }` — принят как механизм
  CapsLock (раздел 4); слои `caps`/`caps_shift` из TOML теперь используются
  как Group2 (в отличие от upstream, где они проигнорированы);
- пустых `key`-строк нет (r5c8 отсутствует везде, как SC 28 в KLC).

Ошибки и спорные места (не копировать):

1. `ulo_combo`, `key <AC08>`: уровни 3–4 заданы **строковыми литералами**
   `" => "` / `"->"`. Массив `symbols[]` принимает только keysym
   (имя или `UXXXX`); строка из двух символов — почти наверняка ошибка
   `xkbcomp` (проверить при реализации шагом из раздела 8;
   `xkbcomp` на Windows недоступен).
2. Во всех 3 файлах: `modifier_map Mod5 { <LVL3> };`, но клавиша `<LVL3>`
   нигде не определена — висячий modifier_map (ошибка/предупреждение
   `xkbcomp`). Рядом стоящий `modifier_map Mod5 { <RALT> };` корректен.
3.    `ulo_eng`, `key <AC08>`: лигатуры тихо ужаты до `U003E`/`U003E`
   (`>` вместо `=>`/`->`, комментарий при этом claims `=> ->`) —
   молчаливое искажение без предупреждения. Наш генератор вместо этого
   даёт `W_LINUX_LIGATURE_FALLBACK` на ячейку и пустой уровень (раздел 5).
4. `ulo_eng`, `key <AB02>`: уровень 4 дублирует уровень 3 (`U00D7`),
   хотя по сетке там `@None`; рядом `key <AE05>` честно оставлен
   трёхуровневым. Непоследовательно; наше правило — хвост `-1`
   опускается всегда.
5. Отсутствуют `LSGT`, `KPDL`, `AC11`: работает только за счёт
   `include "pc+us..."` (наследует системный `us` — там на AC11 апостроф).
   Наш генератор пишет все 50 позиций явно, пустые — `[ NoSymbol ]`,
   именно чтобы ничего не протекало из include (раздел 3).
6. Цифровой ряд — символы первыми (`[exclam, 1, ...]`), т.е. файлы
   соответствуют `*-inverted.toml`, а не прямым схемам; комментарий
   об этом честно предупреждает («swapped as it is better»).
   Наш генератор следует TOML как есть (прямые и inverted — оба).
7. `ulo_combo` — двухгрупповая архитектура, но с другой семантикой:
   Group1/Group2 = EN/RU (два языка в одном файле). Наша архитектура —
   один TOML = один файл = две группы, где Group1 = базовые слои,
   Group2 = явные caps-слои + дубли уровней 3–4 (для не-букв `@Trans` → копия base)
   (в `ulo_combo` Group2 тоже четырёхуровневая — приём перенят вместе
   с групповым механизмом). Языковое смешение — нет:
   6 схем остаются независимыми.
8. Мелочи: `key<CAPS>` без пробела (валидно, но правим в наш стиль),
   `name[Group1] = "English (EN)"` (пробелы вокруг `=` оставляем
   как в системных файлах — без них).

Вердикт: брать за **golden нельзя** — расходятся порядок base/shift
в цифрах, политика лигатур, групповая структура и часть контента.
Использовать как **референс** (порядок уровней, имена keysym,
`FOUR_LEVEL_ALPHABETIC`, SPCE, `include level3`). Подтверждённые
находки уже внесены в разделы 2–6 выше.
