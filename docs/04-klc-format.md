# Формат `.klc`: исследование по эталонам

Источники: три эталонных файла в `universal-layout/layouts/Windows/Ortho/`
(`Universal Layout Ortho English/Merged/Russian.klc`), сверенные между собой,
плюс открытые тексты KLC системных раскладок (через kbdlayout.info) для
интерпретации `Cap`/`SGCap`. MSKLC SDK-документации в открытом доступе нет,
поэтому ниже — реконструкция по фактам, достаточная для побайтово
совместимой генерации. Все утверждения, помеченные «факт», проверены чтением
эталонов как UTF-16LE.

## 1. Общие свойства файла (факты)

- Кодировка UTF-16LE с BOM (`FF FE`), переводы строк CRLF.
- Разделитель колонок — табуляция. Секции идут в строгом порядке:
  `KBD`, `COPYRIGHT`, `COMPANY`, `LOCALENAME`, `LOCALEID`, `VERSION`,
  `SHIFTSTATE`, `LAYOUT`, `LIGATURE`, `KEYNAME`, `KEYNAME_EXT`,
  `DESCRIPTIONS`, `LANGUAGENAMES`, `ENDKBD`.
- Пустые строки между секциями — как в эталоне (одна пустая строка).
- Комментарии `// ...` после строк `LAYOUT`/`LIGATURE` необязательны для
  MSKLC, но мы их генерируем: они помогают ревью и совпадают с эталонами
  (`// DIGIT ONE, ...`, `// EQUALS SIGN + GREATER-THAN SIGN`).

## 2. Шапка (факты из эталона Merged)

```text
KBD	ULOM	"Universal Layout Ortho Merged"
COPYRIGHT	"© 2026 braindefender"
COMPANY	"braindefender"
LOCALENAME	"en-US"
LOCALEID	"00000409"
VERSION	1.0
```

`KBD` — значение `[msklc].name`. Вторая колонка в кавычках —
`[msklc].description`. `LOCALENAME`/`LOCALEID` — из опциональных
`[msklc].locale_name` / `[msklc].locale_id` с дефолтами `en-US`/`00000409`
(см. `docs/02-toml-schema.md`, раздел 4); `VERSION` — константа `1.0`.

## 3. `SHIFTSTATE` (факт)

Эталоны содержат ровно:

```text
SHIFTSTATE
0	//Column 4
1	//Column 5 : Shft
2	//Column 6 :       Ctrl
6	//Column 7 :       Ctrl Alt
7	//Column 8 : Shft  Ctrl Alt
```

Пять состояний. Их порядок задаёт смысл колонок `LAYOUT` (0,1,2,6,7) и
номера `Mod#` в `LIGATURE`: состояние `0` — это `Mod# 0`, `1` — `Mod# 1`,
`2` — `Mod# 2`, `6` — `Mod# 3`, `7` — `Mod# 4`. Подтверждено фактом:
лигатуры `@FatArr` (слой `altgr`, т.е. состояние 6) записаны как `K  3 ...`,
а `@ThinArr` (слой `altgr_shift`, состояние 7) — как `K  4 ...`.

Генератор всегда пишет этот блок дословно. Никаких других состояний
(например, `Ctrl+Shift`) наши схемы не используют.

## 4. `LAYOUT`: строка, колонки, `Cap` (факты + интерпретация)

Заголовок эталона:

```text
LAYOUT		;an extra '@' at the end is a dead key
//SC	VK_		Cap	0	1	2	6	7
//--	----		----	----	----	----	----	----
```

Каждая клавиша — одна строка: `SC, VK, Cap, col0, col1, col2, col6, col7`.
Строки идут в порядке возрастания scancode (см. таблицу позиций в
`docs/05-position-map.md`). Коды — строчные 4-hex (`002d`, `00ab`, `2014`),
пусто — `-1`, лигатура — `%%`.

**Колонки состояний.** `col0 = base`, `col1 = base_shift`,
`col2 = Ctrl-колонка` (фиксирована позицией, см. ниже), `col6 = altgr`,
`col7 = altgr_shift`. Факт: `SPACE` — `0020 0020 0020 00a0 -1`;
`OEM_4` (`,`/`;`) — `002c 003b 001b 002c 003b`;
`OEM_5` (`/`/`|`) — `002f 007c 001c 005c 00a6`.

**Ctrl-колонка (col2).** В эталонах она не выводится из TOML, а задана
позицией: большинство клавиш `-1`, четыре символьные клавиши несут
управляющие коды (`OEM_4 -> 001b`, `OEM_6 -> 001d`, `OEM_5/OEM_102 -> 001c`),
`SPACE` несёт `0020`, `DECIMAL` — `-1`. Это стандартные Ctrl-привязки
Windows (`Ctrl+[` = ESC и т.п.). Генератор берёт их из таблицы позиций
как константы; валидатор их не проверяет. Риск: если будущая схема положит
на эти позиции буквы, Ctrl-коды станут неверными — тогда таблицу придётся
пересмотреть; валидатор должен будет предупреждать `W_CTRL_STALE`.
Сейчас все примеры консистентны, поэтому правило простое.

**`Cap`.** Два значения: `0` и `SGCap`. Факты:

- `Cap=0`: цифровая строка (02–0d), нижний ряд (`OEM_3`, `OEM_5`, `SPACE`,
  `OEM_102`, `DECIMAL`) и две символьные клавиши среднего ряда
  (`OEM_4`, `OEM_6`, т.е. `,`/`;` и `.`/`:`). CapsLock такие клавиши
  не меняет, строк-расширений у них нет.
- `Cap=SGCap`: все 30 клавиш буквенной зоны (TOML-строки 2–4, все 10 колонок
  каждой). Каждая такая строка сопровождается строкой-расширением
  `-1 -1 0 <caps> <caps_shift>` на следующей строке. Пример (Merged, Q):
  основная строка `10 Q SGCap q Q -1 03c8 03a8`, расширение
  `-1 -1 0 0439 0419` (й/Й из слоёв `caps`/`caps_shift`).
- Если слоёв `caps` нет (English): расширение всё равно есть, но содержит
  `shift`/`base` в этом порядке: `-1 -1 0 Q q`. Это и есть `caps=shift`:
  Caps даёт заглавную, Caps+Shift — строчную. Факт проверен на всех 30
  клавишах English.klc (включая символьную `OEM_1` с `~`/`≈`: расширение
  `2248 007e`, т.е. тоже swap).
  Историческая пометка: swap для символьных клавиш (`~`/`≈`, `&`, `[`, `]`)
  признан неверным — системный CapsLock затрагивает только буквы.
  Поэтому слои `caps`/`caps_shift` обязательны, а не-буквы размечаются
  `@Trans` (`Cap 0` без расширения, см. `docs/02`, `docs/06`).
- Вывод: `Cap` определяется **позицией** (буквенная зона или нет),
  а не символом. Даже `~` в буквенной зоне получает `SGCap`.

Замечание про `Cap=1`: в системных раскладках без AltGr буквы имеют `Cap=1`
(без расширений). Наши раскладки всегда имеют AltGr, поэтому всегда `SGCap`
в буквенной зоне — так делают и эталоны. Генератор не использует `Cap=1`.

## 5. `LIGATURE` (факты)

```text
LIGATURE
//VK_	Mod#	Char0	Char1	Char2	Char3
//----		----	----	----	----	----
K		3	003d	003e		// EQUALS SIGN + GREATER-THAN SIGN
K		4	002d	003e		// HYPHEN-MINUS + GREATER-THAN SIGN
```

Правила, выведенные из эталонов:

1. Строка лигатуры: `VK, Mod#, коды`. `VK` — имя виртуального кода клавиши
   (`K`), не scancode. `Mod#` — индекс состояния в `SHIFTSTATE` (3 для
   `altgr`, 4 для `altgr_shift`).
2. В `LAYOUT` на месте лигатуры стоит `%%` в соответствующей колонке
   (Merged: `25 K SGCap k K -1 %% %%`).
3. Коды — те же 4-hex, что в `LAYOUT`, по числу символов значения лигатуры
   (здесь по два). Пустые `Char2`/`Char3` просто отсутствуют (не `-1`).
4. Комментарий — имена символов через ` + `.
5. Сортировка: по scancode клавиши, затем по `Mod#`. В эталоне обе лигатуры
   на одной клавише `K`, порядок 3 затем 4.

## 6. Подвал (факты)

`KEYNAME` и `KEYNAME_EXT` — статические таблицы scancode→имя (Esc, Backspace,
..., F1–F24, Num-блок, Windows-клавиши). Во всех трёх эталонах идентичны;
генератор пишет их дословно из шаблона.

```text
DESCRIPTIONS
0409	Universal Layout Ortho Merged
LANGUAGENAMES
0409	Universal Layout Ortho
ENDKBD
```

`DESCRIPTIONS` — `main.name`. `LANGUAGENAMES` — `[msklc].language_names`,
если задано, иначе fallback на `main.name`. В эталонах — `main.name` без
последнего слова (`Merged`/`English`/`Russian` отброшены, остаётся
`Universal Layout Ortho`). Это эвристика, которую генератор **не должен**
повторять молча: явный источник имени языка — `[msklc].language_names`.
Для схем без поля действует исторический fallback (`LANGUAGENAMES` =
`DESCRIPTIONS`), отличие таких файлов от эталона фиксируется в тестах
как известное.

## 7. Что MSKLC проверяет при загрузке (практические следствия)

- Неизвестный `VK` или дублирующийся `SC` — ошибка загрузки. Поэтому таблица
  позиций — константа, а не вывод из символов.
- `%%` без соответствующей строки `LIGATURE` (и наоборот) — ошибка.
  Генератор строит оба места из одного списка лигатур, рассинхрон исключён.
- `SGCap` без строки-расширения — ошибка. Генератор всегда пишет расширение
  для каждой `SGCap`-строки.
- Файл без BOM или с LF вместо CRLF MSKLC обычно открывает, но эталоны —
  UTF-16LE+BOM+CRLF; генератор повторяет эталоны точно.
